XSS 無疑是前端最常聽到的資安議題之一，就像資安冰山露出水面的那一角，幾乎一談到前端安全就會先碰到它。這篇會從幾個實際範例開始，看看惡意內容怎麼進入網頁、瀏覽器為什麼會執行，以及框架替我們擋掉了哪些風險。

## XSS 到底是什麼？

> [Cross-site scripting（XSS）（MDN 說明）](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/XSS)
>
> [本文範例程式碼：blog-labs](https://github.com/LING-JUN-HAO/blog-labs/tree/main/xss)

XSS 的全名是 **Cross-Site Scripting（跨網站指令碼攻擊）**。簡單來說，就是攻擊者控制的內容進入網頁後，被瀏覽器當成 JavaScript 執行。

提到 XSS，很多人第一個想到的就是插入 `<script>` 標籤，但攻擊方式其實不只這一種。同一段內容放在 HTML 的不同位置，瀏覽器解讀的方式也會不一樣。就算完全沒有 `<script>`，還是可能觸發 XSS。

本文先從三種常見的注入位置來看。

- HTML 屬性
- HTML 內容
- JavaScript 程式碼

### 從 HTML 屬性進行 XSS 攻擊

先來看 HTML 屬性的情況。這個網頁會從網址參數取得 `class` 名稱，再用 `innerHTML` 把內容放進畫面。

```html
<div id="content"></div>

<script>
  const clazz = new URLSearchParams(location.search).get('clazz');

  document.querySelector('#content').innerHTML =
    `<div class="${clazz}">Demo</div>`;
</script>
```

如果 `clazz` 的值是 `container`，最後產生的 HTML 會長這樣。

```html
<div class="container">Demo</div>
```

問題就出在 `clazz` 被直接放進雙引號包住的 `class` 屬性。網址參數只要帶有 `"`，就能提前結束原本的屬性值，再接上新的屬性。

攻擊者可以把 `clazz` 改成這串內容。

```text
" tabindex=1 onfocus="alert(1)" x="
```

拼接後的 HTML 會變成這樣。

```html
<div class="" tabindex=1 onfocus="alert(1)" x="">Demo</div>
```

拆開來看，就會比較清楚每一段在做什麼。

- **`"`** 先把原本的 `class` 屬性關掉，後面的內容就能變成新的 HTML 屬性。
- **`tabindex=1`** 讓原本不一定能取得焦點的 `<div>` 可以透過鍵盤或程式取得焦點。
- **`onfocus="alert(1)"`** 告訴瀏覽器，元素取得焦點時要執行 `alert(1)`。
- **`x="`** 接住模板原本留在後面的引號，讓最後產生的 HTML 維持完整結構。

這裡的 `onfocus` 屬於 **Inline Event Handler（行內事件處理器）**，也就是直接把事件發生時要執行的 JavaScript 寫在 HTML 屬性上。

HTML 成功插進頁面後，JavaScript 也不一定會馬上執行。這個範例要等到 `<div>` 取得焦點，才會真的跳出 `alert`。如果網站設定了 Content Security Policy（CSP），而且沒有允許行內事件處理器，這段程式碼就會被瀏覽器擋下來。

這個例子完全沒有用到 `<script>` 標籤。攻擊者只要能跳出原本的屬性值，再塞進可以執行 JavaScript 的新屬性，就可能造成 XSS。

### `javascript:` 偽協議

> [javascript: URLs（MDN 說明）](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Schemes/javascript)

HTML 屬性還有另一種情況。就算不用引號跳出原本的屬性值，只要網站允許使用者控制完整的連結網址，攻擊者就可能把 `href` 換成 `javascript:`。

```html
<a href="javascript:alert(1)">查看內容</a>
```

`javascript:` 看起來像一般網址，使用者點下連結後，瀏覽器執行的卻是後面的 JavaScript。這段內容沒有 `<`、`>` 或引號，只做 HTML 編碼也擋不住。處理完整網址時，還要先解析 URL，再檢查協議，只允許 `http:`、`https:` 等網站真的需要的類型。

### 從 HTML 內容進行 XSS 攻擊

> [Element.innerHTML（MDN 說明）](https://developer.mozilla.org/en-US/docs/Web/API/Element/innerHTML#security_considerations)

再來看看 HTML 內容。這段程式會讀取網址中的 `content`，再直接交給 `innerHTML` 顯示。

```html
<div id="content"></div>

<script>
  const content = new URLSearchParams(location.search).get('content');

  document.querySelector('#content').innerHTML = content;
</script>
```

`innerHTML` 有一個容易讓人誤會的解析行為。它會把傳入的字串解析成 DOM 節點，但透過這種方式插入的 `<script>` 不會執行。就算把 `content` 改成 `<script>alert(1)</script>`，DOM 中只會產生 `<script>` 元素，不會跳出 `alert`。這不代表 `innerHTML` 是安全的，其他能執行 JavaScript 的 HTML 仍然可能造成 XSS。

把 `content` 換成這段內容。

```html
<img src=x onerror=alert(1)>
```

當 `src=x` 載入失敗，瀏覽器就會觸發 `error` 事件，接著執行 `onerror` 裡的 `alert(1)`。

### 從 JavaScript 程式碼進行 XSS 攻擊

> [EJS Tags（EJS 官方文件）](https://ejs.co/docs/)

最後是 JavaScript 程式碼。例如 Express 把網址參數 `name` 傳進 EJS，模板又用 `<%- %>` 將內容原樣放進 JavaScript 字串，攻擊者就能利用引號提前結束這段字串。

```ejs
<script>
  const name = '<%- name %>';
</script>
```

這裡跟上面的 `innerHTML` 範例不太一樣。透過 `innerHTML` 動態插入 `<script>` 時，瀏覽器不會執行裡面的 JavaScript。EJS 則是在伺服器端把 `name` 拼進回傳的 HTML，瀏覽器收到回應後會從頭解析整份文件，遇到 `<script>` 時就會執行其中的程式碼。

把 `name` 換成這串內容。

```text
'; alert(1); //
```

瀏覽器最後收到的程式碼會長這樣。

```html
<script>
  const name = ''; alert(1); //';
</script>
```

開頭的 `'` 會結束原本的字串，接著執行 `alert(1)`。最後的 `//` 會把剩下的內容變成註解，避免後方多出來的引號造成語法錯誤。

## 常見的 XSS 分類

> [Cross Site Scripting（XSS）（OWASP 說明）](https://community.owasp.org/attacks/xss/)
>
> [DOM based XSS Prevention Cheat Sheet（OWASP）](https://cheatsheetseries.owasp.org/cheatsheets/DOM_based_XSS_Prevention_Cheat_Sheet.html)

除了注入位置，XSS 也常被介紹成反射型、儲存型與 DOM 型。不過，這三個名稱不是完全互斥的分類。反射型與儲存型主要描述惡意內容如何送進頁面，DOM 型則是在描述漏洞發生於前端程式操作 DOM 的過程。以下仍沿用這組常見名稱，分別看看它們的攻擊流程。

### 反射型 XSS（Reflected XSS）

反射型 XSS 的內容通常藏在網址參數裡，後端收到後又直接放進回傳的 HTML。因為內容不會被存起來，攻擊者得想辦法讓使用者點開帶有攻擊內容的連結。

沿用前面的 Express 與 EJS 範例，後端先把網址參數 `name` 傳進模板。

```ts
app.get('/', (req, res) => {
  res.render('index', { name: req.query.name });
});
```

EJS 再用 `<%- %>` 將 `name` 原樣放進 HTML。

```ejs
<p>Hello, <%- name %></p>
```

打開 `/?name=Antonio` 時，頁面會顯示 `Hello, Antonio`。如果網址改成 `/?name=<script>alert(1)</script>`，這段 `<script>` 就會跟著出現在伺服器回傳的 HTML，並在瀏覽器解析頁面時執行。

### 儲存型 XSS（Stored XSS）

如果惡意內容先被存進資料庫，之後又在沒有針對輸出位置處理的情況下放回頁面，就可能變成儲存型 XSS。

留言板就是很常見的情境。攻擊者送出一則內容為 `<img src=x onerror=alert(1)>` 的留言，後端收到後直接存進資料庫。EJS 顯示留言時，又透過 `<%- %>` 把內容原樣放進 HTML。

```ejs
<% comments.forEach((comment) => { %>
  <article><%- comment.content %></article>
<% }); %>
```

這段惡意內容會一直留在留言板裡。之後不管是誰打開頁面，瀏覽器都會解析這張圖片，並在載入失敗時執行 `onerror` 裡的 JavaScript。

### DOM 型 XSS（DOM-based XSS）

DOM 型 XSS 的關鍵在於前端程式把不受信任的資料交給危險的 DOM API，後端不一定會參與其中。前端從網址讀出參數後，如果又透過 `innerHTML` 寫進頁面，就可能讓惡意內容執行。

```html
<div>Hello, <span id="name"></span></div>
<script>
  const name = new URLSearchParams(location.search).get('name');

  // ?name=<script>alert(1)</script>       → 不會執行
  // ?name=<img src=x onerror=alert(1)>    → 會跳出 alert
  document.querySelector('#name').innerHTML = name;

  // 換成 textContent，上面兩種輸入都只會顯示成純文字
  // document.querySelector('#name').textContent = name;
</script>
```

## XSS 可能造成什麼影響？

> [Set-Cookie 的 HttpOnly 設定（MDN 說明）](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie#httponly)

前面的範例一直使用 `alert`，只是為了確認 JavaScript 真的能執行。攻擊者一旦能在頁面上跑自己的程式碼，通常就能存取網站原有 JavaScript 可以碰到的資料與功能。

- 讀取頁面資料：攻擊者可以拿到畫面上的內容，也能讀取 `localStorage` 裡的 Token。
- 偷走 Cookie：如果登入 Cookie 沒有設定 `HttpOnly`，攻擊者可以透過 `document.cookie` 讀出來，再傳到自己的伺服器。
- 冒用使用者操作：就算 Cookie 設定了 `HttpOnly`，攻擊程式碼還是能在頁面上呼叫 API。瀏覽器會自動帶上登入 Cookie，後端看到的就是一個已登入的請求。
- 修改畫面：攻擊者也能換掉按鈕、表單或連結，把使用者輸入的資料送到其他地方。

`HttpOnly` 可以讓 JavaScript 讀不到 Cookie，降低登入憑證被偷走的風險，但它不會阻止 XSS，也擋不住攻擊者直接在頁面上操作 API。

## 框架幫我們處理了什麼？以 Angular 為例

> [Angular Security 官方文件](https://angular.dev/best-practices/security)

前端框架通常不會直接把模板中的資料當成 HTML 執行。這裡以 Angular 為例，用同一段內容比較模板插值、`[innerHTML]` 與主動繞過安全檢查後的差別。

```ts
content = '<strong>Hello</strong><img src=x onerror=alert(1)>';
```

### 模板插值只會顯示文字

先把 `content` 放進模板插值。

```html
<div>{{ content }}</div>
```

畫面會直接顯示 `<strong>` 與 `<img>` 這些字串，不會把它們當成 HTML。這也是平常顯示使用者名稱、留言或其他純文字時，最安全也最簡單的做法。

### `[innerHTML]` 會先清理內容

如果真的需要顯示 HTML，可以使用 `[innerHTML]`。

```html
<div [innerHTML]="content"></div>
```

Angular 會保留 `<strong>`，並在寫入 DOM 前拿掉 `onerror` 這類危險內容。如果清理後的 HTML 和原本不同，開發模式的 Console 會顯示警告，提醒你有內容被拿掉。`content` 本身不會被修改，只有最後寫進 DOM 的結果會改變。

### `[href]` 會清理危險網址

Angular 不只會清理 HTML，也會檢查綁定到網址屬性的內容。把 `javascript:alert(1)` 放進連結的 `[href]` 時，Angular 會把它判斷成危險網址。

```ts
dangerousUrl = 'javascript:alert(1)';
```

```html
<a [href]="dangerousUrl">查看內容</a>
```

從 DevTools 查看元素時，`href` 會變成 `unsafe:javascript:alert(1)`。瀏覽器不再把它當成可執行的 `javascript:` 網址，點下連結也不會跳出 `alert`。前面那個 `javascript:` 偽協議，在 `[href]` 綁定裡就會被 Angular 攔下來。

### `bypassSecurityTrustHtml` 是繞過保護

> [DomSanitizer（Angular API）](https://angular.dev/api/platform-browser/DomSanitizer)

`bypassSecurityTrustHtml` 的名字很容易讓人以為它會清理 HTML，但它做的事情剛好相反。呼叫這個方法，等於直接告訴 Angular「這段內容我已經檢查過，可以相信」。

```ts
import { inject } from '@angular/core';
import { DomSanitizer } from '@angular/platform-browser';

private readonly sanitizer = inject(DomSanitizer);

trustedContent = this.sanitizer.bypassSecurityTrustHtml(this.content);
```

```html
<div [innerHTML]="trustedContent"></div>
```

一旦使用這個方法，Angular 就不會再移除 `onerror`。如果 `content` 來自網址、API 或使用者輸入，等於自己關掉原本的防護。只有確定內容可信、清楚它如何產生，而且真的需要保留那些 HTML 時，才適合使用。

## 如何防範 XSS？

> [Content Security Policy（MDN 說明）](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)
>
> [Trusted Types API（MDN 說明）](https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API)

用了框架不代表 XSS 就不會發生，框架只是先幫我們擋掉一些常見風險。像前面的 `[innerHTML]`，Angular 會拿掉 `onerror` 這類危險屬性，但只要直接操作 DOM 或繞過安全檢查，這些保護就不一定還在。

- 先確認資料最後會進入哪個位置。HTML 內容、HTML 屬性、JavaScript 與 URL 的解析方式不同，不能用同一種編碼或過濾方式處理所有情況。
- 內容是純文字時，使用 Angular 模板插值；操作一般 DOM 元素時，則使用 `textContent`。
- 真的需要顯示 HTML 時，讓 Angular 的 `[innerHTML]` 進行內容清理，不要自己用正規表達式過濾標籤。
- 網址資料透過 Angular 的 `[href]` 綁定。離開框架自行處理完整網址時，使用 `new URL()` 解析，再限制網站允許的協議。
- 不要把網址參數、API 回應或使用者輸入傳給 `bypassSecurityTrustHtml`。
- 盡量不要直接操作 `document`、`ElementRef.nativeElement`，也不要把不受信任的內容交給 `innerHTML`、`outerHTML` 或 `insertAdjacentHTML`。這些操作不一定會經過 Angular 的防護。
- CSP 會告訴瀏覽器哪些程式碼可以執行。設定嚴格的規則後，沒有正確 nonce 或 hash 的 `<script>`，以及 `onerror` 這類行內事件處理器都不會執行。它是額外的防線，不能取代前面的處理。
- Trusted Types 則是守在 `innerHTML` 這類危險 API 前面。啟用後，這些 API 不能再接收普通字串，而是要先經過指定的 policy。它不會自行清理內容，policy 仍然要實作正確的檢查或 sanitization。
- 登入 Cookie 設定 `HttpOnly`，轉帳、改密碼這類重要操作則要求重新驗證。就算 XSS 真的發生，也能縮小影響範圍。

## 總結

XSS 最容易讓人誤會的地方，是以為只要擋住 `<script>` 就夠了。實際上，行內事件處理器與 `javascript:` 網址都能執行程式碼。同一段內容放在 HTML、屬性、JavaScript 或 URL 中，瀏覽器也會用不同的方式解讀，防護方式必須跟著輸出位置調整。

Angular 已經替模板插值、`[innerHTML]` 與 `[href]` 做了不少處理，沿用框架提供的安全寫法，就能先擋下大部分常見風險。真正需要小心的是直接操作 DOM，或使用 `bypassSecurityTrustHtml` 繞過安全檢查。當我們主動跳過框架的防護，也要自己承擔檢查內容的責任。
