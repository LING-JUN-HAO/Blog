[上一篇文章](/XSS/)提到，框架預設的字串編碼與 sanitize 是防止 XSS 的第一道防線。不過，這道防線靠的是每一行程式都寫對。專案裡只要有一處誤用 `innerHTML`、一個舊頁面忘了處理輸入，或載入的第三方程式碼出了問題，攻擊者的 JavaScript 就能在頁面上執行，讀走畫面上的資料，再傳到其他網站。

程式碼不可能永遠沒有漏洞，所以還需要一道不靠程式寫對的防線。CSP（Content Security Policy，內容安全政策）讓網站事先告訴瀏覽器，頁面能執行哪些程式碼、能從哪裡載入資源。就算攻擊者成功注入內容，瀏覽器也會照這份規則，把不在名單內的東西擋下來。

> [Content Security Policy Cheat Sheet（OWASP）](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html)
>
> [本文範例程式碼：blog-labs](https://github.com/LING-JUN-HAO/blog-labs/tree/main/csp)

## CSP 是什麼？

CSP 是伺服器透過 HTTP Response Header 送給瀏覽器的一組規則。瀏覽器收到頁面時會一起讀取這些規則，之後頁面上的每一段 script、每一張圖片、每一次 `fetch()`，都要先通過檢查才會執行或載入。

攻擊者如果能把下面的 `<img>` 放進頁面，圖片載入失敗後就會執行 `onerror`。

```html
<img src="invalid" onerror="alert(document.domain)">
```

伺服器加上下面這行 Header 後，瀏覽器只會執行同源的外部 JavaScript 檔案，寫在 HTML 裡的行內程式碼和事件處理器都不會執行。

```http
Content-Security-Policy: script-src 'self'
```

`onerror` 仍然會出現在 DOM 裡，但裡面的 JavaScript 不會執行，Console 也會顯示違反 CSP 的錯誤。注入點沒有消失，只是攻擊者塞進來的程式碼跑不起來。

CSP 不會修掉 XSS，注入點還是要回到程式裡修。它做的是在「程式寫錯」和「攻擊成功」之間多加一道關卡。

## CSP 的規則怎麼寫？

一份 CSP 由多個 directive 組成，每個 directive 後面接允許的來源，directive 之間用分號隔開。

```http
Content-Security-Policy: script-src 'self' https://cdn.example.com; img-src 'self' data:
```

這段規則代表 JavaScript 只能來自本站與 `https://cdn.example.com`，圖片只能來自本站或 `data:` 網址。

常見的來源寫法有以下幾種。

| 寫法 | 意思 |
| --- | --- |
| `'self'` | 與目前頁面同源（協定、網域、Port 都相同） |
| `'none'` | 什麼都不允許 |
| `https://api.example.com` | 指定的網域，也可以用 `https://*.example.com` 包含子網域 |
| `https:`、`data:` | 指定協定，例如所有 HTTPS 網址或 `data:` 圖片 |
| `'nonce-…'`、`'sha256-…'` | 只允許帶有指定 nonce 或符合 hash 的程式碼，後面會再說明 |

`'self'`、`'none'` 這類關鍵字要加單引號，網域和協定則不用。少了引號的 `self` 會被當成一個叫 self 的網域，規則就不會照預期運作。

### 常用的 directive

| Directive | 控制的內容 | 常見情境 |
| --- | --- | --- |
| `default-src` | 沒有另外設定時的預設來源 | 先限制所有資源的預設範圍 |
| `script-src` | JavaScript 與行內事件 | 自己的程式、CDN 上的套件、第三方 SDK |
| `style-src` | CSS 與行內樣式 | 樣式檔、行內 `style`、CSS-in-JS |
| `img-src` | 圖片來源 | CDN、物件儲存、`data:` 圖片 |
| `font-src` | 網頁字型來源 | 自架字型或第三方字型服務 |
| `connect-src` | `fetch`、XHR、WebSocket、SSE | API、即時連線、分析工具回傳資料 |
| `frame-src` | 頁面可以嵌入的 frame | 金流、影音、第三方登入畫面 |
| `worker-src` | Worker | Web Worker、Service Worker |
| `object-src` | `<object>`、`<embed>` | 現在幾乎用不到，通常直接設成 `'none'` |
| `frame-ancestors` | 哪些網站可以嵌入目前頁面 | 防止頁面被其他網站放進 iframe |

以下是一份簡化的 CSP。

```http
Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  connect-src 'self' https://api.example.com;
  img-src 'self' data: https://images.example.com;
  style-src 'self';
  font-src 'self';
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none';
  form-action 'self';
```

這份設定不能直接套到所有網站。第三方分析工具、登入服務、客服元件與外部字型，都可能需要額外開放來源。

`default-src` 會替載入資源的 directive 提供預設值。例如沒有設定 `img-src` 時，圖片會套用 `default-src`；沒有設定 `script-src` 時，JavaScript 也會套用 `default-src`。

`base-uri`、`form-action` 和 `frame-ancestors` 管的不是資源載入，不會沿用 `default-src`，要另外設定。

- **`base-uri`。** 限制頁面可以使用哪些 `<base>`。如果攻擊者插入下面的內容，原本連到本站的 `/account` 會改成 `https://attacker.example/account`。網站不需要 `<base>` 時，可以設定成 `base-uri 'none'`。

    ```html
    <base href="https://attacker.example/">
    <a href="/account">會員中心</a>
    ```

- **`form-action`。** 限制表單可以送到哪裡。即使設定了 `default-src 'self'`，沒有設定 `form-action` 的表單仍可能把資料送到其他網站。表單只會送回本站時，可以設定成 `form-action 'self'`。
- **`frame-ancestors`。** 限制哪些網站可以把目前頁面放進 iframe，用來降低 Clickjacking（點擊劫持）的風險。不允許任何網站嵌入時，可以設定成 `frame-ancestors 'none'`。

## `connect-src` 和 CORS 有什麼不同？

前端用 `fetch()` 呼叫 API 時，很容易把 `connect-src` 和 CORS 混在一起。

`connect-src` 是頁面自己決定可以連線到哪些目的地。API、WebSocket 或 SSE 不在清單裡，瀏覽器在送出請求前就會擋下來。

CORS 則是 API 伺服器決定哪些來源的 JavaScript 可以讀取它的回應。所以 API 的 CORS 設定沒問題，頁面也不一定發得出請求，只要 `connect-src` 沒有允許這個 API，瀏覽器一樣會擋下來。

CSP 保護頁面，避免被注入的程式碼把資料送到其他網站；CORS 保護 API，避免其他網站讀到不該讀的回應。

## 為什麼不該直接加上 `unsafe-inline`？

`script-src` 會擋下行內 `<script>`、`onclick`、`onerror` 和 `javascript:` URL。網站加上 CSP 後如果無法運作，直接加入 `'unsafe-inline'` 看起來最快。

```http
Content-Security-Policy:
  script-src 'self' 'unsafe-inline'
```

但 `'unsafe-inline'` 會連攻擊者注入的行內 JavaScript 一起放行，前面 `onerror` 的例子就又能執行了。`'unsafe-eval'` 也一樣，它會打開 `eval()`、`new Function()` 這類把字串當成程式碼執行的功能。

有些開發伺服器或舊套件會用到 `eval()`，正式環境卻不一定需要。CSP 要拿正式建置的結果測試，不要因為開發環境報錯，就在正式政策加上 `'unsafe-eval'`。

## nonce、hash 與 `strict-dynamic`

頁面真的需要行內 script 時，可以使用 nonce 或 hash，只允許指定的程式碼執行，不必整個打開 `'unsafe-inline'`。

> [Content Security Policy（MDN）](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)

### nonce

nonce 是伺服器每次回應都重新產生的隨機值。Header 與 `<script>` 上的 nonce 相同，瀏覽器才會執行這段程式碼。攻擊者猜不到這次的 nonce，注入的 script 就不會執行。

```http
Content-Security-Policy:
  script-src 'nonce-r4nd0m-value'
```

```html
<script nonce="r4nd0m-value">
  window.__APP_CONFIG__ = { apiBase: '/api' };
</script>
```

nonce 必須無法預測，而且每次回應都要不同，所以適合由伺服器產生 HTML 的網站。部署成靜態檔案的網站，沒辦法在每次請求時替 HTML 換上新的 nonce。

### hash

hash 依照 script 的完整內容計算。Header 只允許符合特定 hash 的程式碼，內容多一個空白或換行，hash 就會不同。

```http
Content-Security-Policy:
  script-src 'sha256-{HASH}'
```

靜態網站可以在建置時替行內 script 算出 hash，但內容一改，Header 也要跟著更新，所以 hash 的計算和 CSP 設定最好放在同一套建置流程裡。

### `strict-dynamic`

通過 nonce 或 hash 驗證的 script，有時還會動態建立其他 `<script>`，例如分析工具的載入程式。加入 `'strict-dynamic'` 後，瀏覽器會信任由這些 script 載入的程式碼，不必把每個動態資源都列進來源清單。

```http
Content-Security-Policy:
  script-src 'nonce-{RANDOM}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
```

OWASP 建議的 Strict CSP 就是這種寫法。網域清單只要開放了某個 CDN，攻擊者就可能拿那個 CDN 上剛好能利用的檔案繞過 CSP。改用 nonce 或 hash 指定信任的起點，再由 `'strict-dynamic'` 把信任傳下去，就不用維護那份清單。

## Trusted Types 限制字串進入危險 API

`script-src` 管的是瀏覽器可以執行哪些程式碼，但 DOM XSS 常常是自己的程式把攻擊者控制的字串交給 `innerHTML`、`document.write()` 這類 API 造成的。這些接收危險內容的位置稱為 injection sink，Trusted Types 可以限制它們接受的資料型別。

> [Trusted Types API（MDN）](https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API)

CSP 加入以下規則後，這些 API 不再接受一般字串，只接受由 `app-policy` 建立的 `TrustedHTML`、`TrustedScript` 或 `TrustedScriptURL`。

```http
Content-Security-Policy:
  require-trusted-types-for 'script';
  trusted-types app-policy;
```

原本直接指定字串的程式碼會拋出 `TypeError`。

```js
const container = document.querySelector('#container');

container.innerHTML = userInput; // TypeError
```

頁面需要顯示 HTML 時，可以把 sanitize 集中到 policy，再由它建立 `TrustedHTML`。

```js
const policy = trustedTypes.createPolicy('app-policy', {
  createHTML(input) {
    return DOMPurify.sanitize(input);
  },
});

const safeHTML = policy.createHTML(userInput);
container.innerHTML = safeHTML;
```

Trusted Types 本身不會判斷內容是否安全，內容仍要由 `createHTML()` 裡的程式處理。如果 policy 直接回傳原字串，危險內容一樣會被包成 `TrustedHTML`，防護也就失去作用。

它的好處是把散落在專案各處的 DOM 操作，集中到少數幾個 policy 檢查。導入時先用 Report-Only 找出既有的 injection sink，再逐一改寫。Trusted Types 在 2026 年進入 Baseline，舊版瀏覽器可能不支援，不能把它當成唯一的 XSS 防線。

## 先用 Report-Only 觀察

一開始就啟用嚴格政策，原本正常的功能很容易突然壞掉。OWASP 建議先用 `Content-Security-Policy-Report-Only`，瀏覽器會在 Console 列出違反政策的資源，也能把報告送到指定端點，但不會真的擋下來。

```http
Reporting-Endpoints: csp-endpoint="https://example.com/csp-reports"

Content-Security-Policy-Report-Only:
  default-src 'self';
  script-src 'self';
  connect-src 'self' https://api.example.com;
  report-to csp-endpoint;
```

導入時可以按照下面的順序處理。

1. 盤點 script、style、圖片、字型、API、WebSocket 與 iframe 的來源。
2. 先送出 Report-Only Header，操作登入、換頁、表單與第三方服務。
3. 檢查回報，修正行內 script、`eval()` 與過度寬鬆的來源。
4. 確認主要功能都能使用後，再改成正式的 `Content-Security-Policy`。

> [Content Security Policy Level 3（W3C）](https://www.w3.org/TR/CSP3/)

`report-uri` 在 CSP Level 3 中已標示為淘汰，新的做法是搭配 Reporting API 使用 `report-to`。如果還要相容舊瀏覽器，可以同時提供兩者。

## CSP 要設定在哪裡？

CSP 最常由伺服器或部署平台加在 Response Header。沒辦法修改 Header 的環境，也可以在 HTML 的 `<head>` 用 `<meta>` 設定。

```html
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'self'; script-src 'self'"
>
```

`<meta>` 只對它後面載入的內容生效，也不支援 `frame-ancestors`、`report-uri`、`report-to` 和 Report-Only，所以能改 Header 時還是用 Header。

### Nuxt 用 Nuxt Security 處理

nonce 每次回應都要重新產生，hash 也要跟著建置結果更新，自己處理很容易漏掉。Nuxt 專案可以直接安裝 Nuxt Security，它預設就會送出 CSP，並依網站的執行方式改用 nonce 或 hash。

```bash
npx nuxi@latest module add security
```

Nuxt Security 2.x 在 Nuxt 3 和 Nuxt 4 都能用，安裝指令和 `nuxt.config.ts` 的寫法都一樣。Nuxt 4 雖然把程式碼搬進 `app/` 資料夾，但 `nuxt.config.ts` 還是留在專案根目錄，設定不用改。下面的實測用的是 Nuxt 4.6.4 搭配 Nuxt Security 2.7.0。

OWASP 建議的 Strict CSP 在 `nuxt.config.ts` 裡可以這樣寫。

```ts
export default defineNuxtConfig({
  modules: ['nuxt-security'],
  security: {
    nonce: true,
    headers: {
      contentSecurityPolicy: {
        'script-src': ["'nonce-{{nonce}}'", "'strict-dynamic'"],
        'object-src': ["'none'"],
        'base-uri': ["'none'"],
      },
    },
  },
})
```

> [Strict CSP（Nuxt Security）](https://nuxt-security.vercel.app/advanced/strict-csp)

有 Nitro Server 的 SSR 網站，伺服器每次回應都會產生新的 nonce 換掉 `{{nonce}}`，同時加到 Nuxt 輸出的行內 script 和 Header 上。

`nuxt generate` 產生的是靜態檔案，沒有伺服器可以換 nonce。用上面的設定實際跑一次 `nuxt generate`，產出的頁面 `<head>` 多了一個 `<meta>`（hash 省略）。

```html
<meta http-equiv="Content-Security-Policy" content="base-uri 'none'; ...; script-src 'strict-dynamic' 'sha256-fNLG…' 'sha256-xbN/…' 'sha384-gsZo…'; upgrade-insecure-requests;">

<script integrity="sha384-gsZo…" type="module" src="/_nuxt/JNcrj88c.js" crossorigin></script>
```

原本的 `'nonce-{{nonce}}'` 變成了一串 hash。`sha256` 對應頁面裡的行內 script，`sha384` 對應外部的 JS 檔，同一個值也寫在 `<script>` 的 `integrity` 上，瀏覽器下載檔案後會先比對，內容對得上才執行。

`<meta>` 不支援 `frame-ancestors`，所以這裡看不到它。部署到 Vercel 時，Nuxt Security 會另外把完整的 CSP 寫進 Vercel 的 Header 設定，`frame-ancestors` 就改由 Header 送出。

範例自己設定了 `script-src`，如果沒設定，模組預設還會多帶 `'unsafe-inline'` 和 `https:`。這是留給舊瀏覽器的退路，新版瀏覽器看到 nonce、hash 和 `'strict-dynamic'` 就會忽略它們，注入的 `onerror` 一樣不會執行。

裝完之後還有兩件事要確認。

- 第三方 script 要改用 Nuxt 的 `useScript()` 載入，才會被 `'strict-dynamic'` 信任。
- 模組預設還會送出 `X-Frame-Options`、`Cross-Origin-Embedder-Policy` 等其他安全性 Header，可能讓 iframe 或第三方圖片載不進來。

不用模組的話，固定的政策也可以寫在 Nitro 的 `routeRules` 或 Vercel 的 `vercel.json`。不管用哪種方式，最後都要拿正式建置的結果開著 Report-Only 測一次，看哪些東西被擋，再決定怎麼改。

> [Route Rules（Nitro）](https://nitro.build/docs/routing#route-rules)
>
> [Vercel headers 設定](https://vercel.com/docs/project-configuration/vercel-json#headers)

## 總結

CSP 是網站交給瀏覽器的一份白名單，列出頁面可以執行的程式碼、可以載入的資源，以及可以連線的位置。程式裡的防護出現漏洞時，注入的程式碼會被 `script-src` 擋下來；就算真的執行了，`connect-src` 也能讓它把資料傳不出去。

導入時先用 Report-Only 找出網站實際用到的來源，用 nonce 或 hash 取代 `'unsafe-inline'`，把過度寬鬆的設定收緊後，再啟用正式政策。Nuxt 專案可以直接交給 Nuxt Security，但它產出的政策和預設 Header 一樣要實際測過。
